# 참여자 선택 재생 실제 로컬 연동 검증

검증일: 2026-10-22 (한국 시간)

## 적용 브랜치

백엔드 `TEST`에 `Feature/shorts-participant-playback`의 두 기능 커밋을 적용했다.
기존 TEST 인증·H2 설정은 유지했다. 프론트는 `Feature/shorts-participant-playback`을 사용했다.

## 실행 환경

- 프론트: `http://localhost:5173`
- 백엔드: `http://localhost:8081`, `local-test` 프로필
- DB: 독립된 H2 파일 `/tmp/adlips-participant-playback-test.mv.db`
- 파일: `/tmp/adlips-participant-playback-uploads`
- Redis: `127.0.0.1:16379`, 임시 컨테이너 `adlips-participant-playback-redis`
- 검증용 화면: `http://localhost:5173/shorts/902` (프로젝트 1)

기존 로컬 DB를 사용하거나 초기화하지 않았다. 외부 API와 운영 데이터는 사용하지 않았다.
브라우저 요청에 모의 응답을 주입하지 않고 실제 백엔드·미디어 파일을 사용했다.

## 데이터와 API 검증

로컬 테스트 계정 세 명에 각각 피아노·어쿠스틱 기타·드럼 트랙을 만들었다.
각 트랙에는 MIDI와 업로드 WAV 클립이 있으며, 작곡·업로드·참여 제출·승인·발행 API로 생성했다.
세 번째 가짜 계정만 독립 테스트 DB에 추가했다.

다음 항목을 확인했다.

- 선택한 악기 ID와 승인된 참여 설명이 참여자 조회에 표시된다.
- 승인 전 트랙은 선택 재생 API에 포함되지 않는다.
- 프로젝트 비회원도 공개 숏폼의 트랙을 읽을 수 있고, 읽은 뒤에도 비회원으로 남는다.
- 실제 업로드 파일의 CORS 조회가 200이고 프론트 Origin이 허용된다.
- 없는 숏폼은 404, 잘못된 토큰은 401이다.
- 백엔드 상태 확인은 200/UP이다.

## 실제 브라우저 검증

Chrome에서 실제 음원 디코딩과 Web Audio 소스 예약을 관찰했다.

- 최초 전체 선택과 악기·여러 줄 설명 표시
- 한 명 선택 시 해당 참여자의 MIDI와 업로드 오디오만 재생
- 다른 한 명으로 변경 시 이전 참여자 소스 정지
- 세 명 중 두 명 선택 시 두 참여자만 재생
- 패널 재진입 시 선택 유지
- 음소거·소리 복구, 일시정지·재생, 재생 위치 변경
- 모두 해제 시 정지와 재생 버튼 비활성화
- 전체 듣기로 기존 믹스 복귀
- 곡 전환 시 선택과 이전 소스 정리
- 댓글창·참여자 패널 높이 일치: 390×844 화면에서 둘 다 708.953125px (84%)
- 작은 화면 대응: 320×640에서 537.59375px (84%), 가로 넘침 없음

브라우저 검증 중 실제 API 요청 13건에서 오류 응답이 없었고, 브라우저 실행 오류도 없었다.

## 발견·수정

기본 환경 파일의 CORS 설정 때문에 프론트에서 업로드 WAV를 Web Audio로 가져올 때
403/Invalid CORS request가 발생했다. `application-local-test.properties`에 로컬 프론트
Origin을 명시해 수정하고, 실제 파일 요청 및 위 브라우저 시나리오로 재검증했다.

TEST 브랜치 전체 자동화 테스트: 1,029개 통과, 실패·오류·건너뜀 0개.
